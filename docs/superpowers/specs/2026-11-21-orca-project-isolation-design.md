# Orca 프로젝트 격리와 EC2 역할 접근 제한 설계

## 적용 대상과 완료 조건

폴더 목록 패치, Orca의 EC2 메타데이터 접근 제한, 프로젝트별 Orca 실행 계정 분리를 한 릴리스에서 검증한다. EC2는 한 대를 유지한다. 현재 포털의 프로젝트 승인, 저장소 읽기·쓰기 방식, S3 백업과 첨부, SSM 관리 접속을 확인한다. 기존 프로젝트나 미커밋 작업의 폐기, 자격 증명 전송, 승인된 종료 시각의 연장은 이 설계의 전제에 포함하지 않는다.

## 구성 선택

현재 운영 포털은 공유 Orca 브로커에서 페어링을 요청하고 고정 WebSocket 업스트림으로 연결한다. 프로젝트 접근 확인은 포털의 연결 시작 단계에 있고, 작업자도 공유 `orca` 계정으로 실행된다. 포털의 관리자 전용 진입 옵션은 빠르게 적용할 수 있지만 프로젝트별 파일·키를 분리할 수 없다. 한 EC2에서 프로젝트 ID에 각각 대응하는 전용 OS 계정과 Orca 서비스 인스턴스를 운영하는 방식을 사용한다. 운영자가 먼저 전용 인스턴스를 등록하고, 준비한 프로젝트를 확인한 뒤에만 공용 라우팅에서 전환한다.

## 프로젝트 연결과 접근 재검증

- 운영자가 관리하는 읽기 전용 매핑에 프로젝트 ID, 전용 UID, 루프백 포트, 브로커 소켓 위치를 기록한다. 포털 요청은 프로젝트 ID로 매핑을 찾는다. 사용자 요청으로 포트나 소켓 경로를 받을 수 없다.
- 브라우저 WebSocket은 프로젝트 ID가 포함된 포털 경로로 들어온다. 연결 직전과 연결 유지 중에 로그인·개발자 역할·프로젝트 접근 권한을 확인한다. 격리 활성화 이후에는 준비되지 않은 ID, 이전 공유 경로, 직접 런타임 포트 요청을 차단한다.
- 전용 런타임과 키 작업은 프로젝트별 UID로 실행한다. 프로젝트 계정은 서로의 홈과 브로커 소켓을 열 수 없고, 포털은 각 브로커에 필요한 접근 권한만 가진다. 전용 런타임의 포트는 호스트 방화벽으로 외부 유입을 차단하고 계정 사이에 다른 프로젝트 포트로 직접 연결할 수 없도록 호스트 규칙으로 제한한다. 런타임이 중지됐을 때에도 다른 계정이 그 프로젝트에 할당된 포트를 대신 바인드할 수 없는지 검증한다.
- 다른 프로젝트의 작업 과정이나 상태가 로컬 프로세스 목록에서 노출되지 않는지 점검한다. 권한이 없는 프로세스 제어의 거부와 프로세스 목록의 가시성은 각각 검증한다.

## EC2 메타데이터 보호

- Orca 계정과 전용 프로젝트 UID를 대상으로 고정 IPv4·IPv6 IMDS 주소의 출력 트래픽을 제한한다. 전용 nftables 테이블의 교체만 수행한다. 호스트의 다른 방화벽 테이블은 유지한다.
- 전용 OS 계정을 추가할 때 목록을 새로 반영하고 차단을 확인한 뒤 서비스를 시작한다. 기존 공유 Orca 계정은 전환 기간에도 보호한다.
- 포털과 SSM에 필요한 통신은 따로 검증한다. IMDS의 확인은 연결 상태와 HTTP 상태로 제한하며 토큰과 역할 자격 증명을 기록하지 않는다.

## 기존 프로젝트 전환과 복구

1. 현행 EC2와 RDS 가동 상태, 종료 예약, 활성 Orca 세션·작업을 확인한다. 계정, 매핑, 워크트리 상태와 저장소 키의 소유권은 비밀 내용을 읽거나 출력하지 않고 점검한다.
2. 기존 작업과 원격에 없는 변경분을 작업하지 않는 시간에 보존한다. 확인한 프로젝트별 디렉터리·Git 저장소·필요한 키만 전용 계정으로 이관한다. 현재 홈 전체, Orca 페어링 정보, AI 로그인 정보를 새 계정에 복제하는 방법은 피한다. 공유 Git 메타데이터를 가리키는 워크트리는 이관 전에 별도 검증한다.
3. 전용 UID 두 개의 정방향 성공 및 교차 거부, 프로젝트 멤버와 비멤버의 실제 브라우저 연결을 점검한다. 라우팅 전환으로 기존 엔드포인트에 연결했던 사용자는 프로젝트별로 다시 연결해야 한다.
4. 검증 후에만 전체 트래픽을 전환한다. 오류 시 서비스와 라우팅을 이전 상태로 되돌리고, 필요 시 관리자 전용 백업으로 작업 디렉터리·저장소와 키 설정을 복구한다. 되돌린 후 포털·Orca·SSM을 확인한다.

## 릴리스 검증

- HTTP와 WebSocket 양쪽에서 권한 없는 프로젝트 요청을 차단하고, 연결된 사용자의 권한을 취소했을 때 전송을 끊는다.
- 실제 Orca 런타임 둘로 각각의 작업 파일·저장소 키 사용을 확인한다. 상대 파일·키·포트·프로세스 접근 거부를 더미 데이터로 점검한다.
- 실제 Orca UID의 메타데이터 접근이 거부되고 포털 S3 첨부·백업, SSM 관리 연결이 유지된다.
- 폴더 목록 사전점검에서 `CANDIDATE_MATCH`를 확인하고 관리자 화면의 목록 갱신과 포털 상태를 검증한다.

이 문서는 구현 및 전환 설계다. 운영 적용 결과는 배포 이후 별도로 기록한다.

## 로컬 검증과 남은 항목

- 격리 모드를 설정한 포털에서 프로젝트별 라우팅과 권한 없는 프로젝트의 연결 거부를 검증했다. 로컬 WebSocket 중계 중 프로젝트 접근 권한을 회수하면 연결이 코드 `1008`로 종료됐다.
- 해시를 확인한 Orca 1.4.255를 두 합성 UID에서 실행했을 때 각자 할당한 루프백 포트가 응답했다. 같은 임시 구성의 브라우저용 네이티브 페어링은 `runtime_unavailable`로 실패했다. 운영과 동일한 계정별 서비스 실행·브로커 연동으로 다시 검증한다.
- 저장소 작업자와 브로커에 프로젝트별 프로필을 연결했다. 프로젝트 서비스 정의와 전환 순서를 추가하고 스냅샷의 통합 후보 해시를 갱신했다. 격리된 Linux 네트워크에서 포털과 해당 UID의 포트 접근을 허용하고 다른 프로젝트 UID의 접근을 거부했다. 프로젝트 UID에서 기존 공유 포트로의 접속도 거부했다. 일회성 systemd 서비스에서 지정 포트의 바인딩만 허용하고, 다른 예약 포트는 IPv4와 IPv6 모두 거부했다.
- 프로젝트별 서비스의 네이티브 페어링, 기존 작업 공간과 키 이관, 실서버 통합 전환 검증이 남았다. [운영 전환 절차](../../orca-project-cutover.md)

## 2026-11-26 운영 결과

세 전용 런타임의 네이티브 브라우저 페어링, 관리 API 목록 갱신, 포털 경유 프로젝트 WebSocket 업그레이드가 통과했다. 전체 인터페이스 바인딩과 systemd 재시작 후 페어링을 제공했다. 브로커 디렉터리는 0710과 포털 전용 ACL을 사용한다. 작업과 키를 전용 계정으로 이관했다. 운영 권한·IMDS·S3·SSM 결과는 최신 verification.md를 따른다.
