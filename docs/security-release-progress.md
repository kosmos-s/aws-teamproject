# 보안 통합 릴리스 진행 기록

## 2026-11-26 운영 재가동과 진단

사용자가 기존 EC2·RDS를 2시간 가동하고 자동 종료하도록 승인했다. 기존 자동 종료 역할의 신뢰 만료를 새 작업 창에 맞추고 AWS Scheduler 예약 두 개를 확인한 뒤 기존 리소스를 시작했다. 서버 내부 타이머도 EC2 11:09:36 KST, RDS 11:09:06 KST로 설정했다. 11:49 KST 조회에서 EC2와 RDS가 모두 중지됐음을 확인했다.

운영의 연결 대상은 프로젝트 세 개이며, 조회 당시 대기·실행 중인 연결 요청과 저장소 작업은 없었다. 프로젝트 ID 1에 대응하는 전용 OS 계정과 새 프로필을 준비했다. 기존 Orca 설치에서 실행용 아티팩트만 복사했고 기존 작업 디렉터리, 저장소 키, AI 인증, 페어링 프로필을 이관하지 않았다. 전용 계정의 사용자 서비스는 활성이고 할당한 포트에서 응답했다. 다만 브라우저 페어링은 `network_exposure_failed`를 반환했다. 네이티브 런타임의 네트워크 노출 준비가 실패하는 원인을 해결한 뒤 프로젝트별 전환을 진행한다.

외부 유입 차단을 먼저 설정하고 바인딩 방식에 따른 실패 여부를 검사할 진단 스크립트를 로컬에 준비했다. 최초 실행은 자동 승인 검토의 사용량 한도로 차단됐고, 이후 재시도는 자동 종료된 EC2에 SSM 명령을 전송할 수 없어 실행되지 않았다. 이 진단에 포함된 방화벽과 서비스 변경은 아직 적용되지 않았다.

폴더 목록 패치와 IMDS 제한의 두 로컬 커밋은 검증 브랜치에 있다. 프로젝트별 포털·작업자·서비스 전환은 미커밋 상태다. 세 변경의 통합 운영 배포, 전체 프로젝트의 파일·키 이관, `main` 병합·원격 푸시는 남아 있다. 새 가동 시간 승인을 받은 뒤 자동 종료 예약을 다시 검증하고 후속 운영 작업을 진행한다.

## 같은 날 추가 승인 이후

추가 2시간 가동을 승인받아 EC2 종료 예약을 13:51:21 KST, RDS 보조 종료를 13:50:51 KST로 검증했다. 프로젝트 세 개를 전용 계정으로 이관했고 네이티브 브라우저 페어링이 모두 통과했다. 초기 전환 오류에서 원본 복구를 확인한 뒤 재시도했다. 포털 서비스의 브로커 접근을 막던 ACL 마스크도 수정했다. 12:05 KST 사전점검 결과는 `CANDIDATE_MATCH`, 목록 권한은 `root:kosmos-portal`과 `0750`·`0640`이었다. 네 Orca UID의 IMDS 차단, 프로젝트 간 작업·키 디렉터리 접근 거부, 관리자 API의 새 폴더 목록, 인증된 프로젝트 WebSocket 업그레이드, S3 첨부와 업무 백업의 저장·읽기를 검증했다. 임시 세션은 삭제했고 시험 첨부는 정리했다. 업무 백업은 기존 삭제 제한에 따라 S3에 보관됐다. 브라우저 UI에서 파일 편집·터미널 실행, 팀원 세 명의 재접속, 재부팅 복구는 추가 확인 항목이다.
