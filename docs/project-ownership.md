# 프로젝트 소유자와 GitHub 연결

2026-11-14 로컬 구현. main 병합·서버 배포·AWS 변경은 별도 승인 대상이며 아직 이 기능을 운영에 적용하지 않았다.

## 권한

새 프로젝트를 만든 member/admin이 소유자가 된다. 소유자와 관리자는 이름·설명, 공개 범위, 보관/복귀, 소유권 이전, GitHub·Orca 연결과 서버 키를 관리한다. 제한 공개여도 소유자는 포털 자료를 볼 수 있다. 기존 소유자 없는 프로젝트는 관리자가 소유자를 지정한다. 활성 member/admin에게만 이전할 수 있고 소유 프로젝트가 남은 계정은 삭제할 수 없다.

완전 삭제는 관리자만 프로젝트 이름을 다시 입력해 수행한다. 포털 프로젝트·메모·할 일·첨부와 연결 메타데이터를 삭제하고, 실패한 파일 삭제는 기존 삭제 대기열로 재시도한다. Orca 작업 폴더와 GitHub 원격 저장소는 보존한다. 서버 키 제거는 비동기이므로 서버가 꺼져 있으면 다음 작업자 실행까지 대기한다. GitHub에 등록된 Deploy key는 GitHub에서 별도로 삭제해야 한다.

## 사용 순서

1. 프로젝트 추가 시 선택 항목인 GitHub 주소에 `https://github.com/소유자/저장소`를 입력한다. 프로젝트·소유자·연결 요청을 함께 저장한다. 빈 주소면 프로젝트만 생성한다.
2. 프로젝트 카드의 **프로젝트 관리**를 연다. 공개 저장소는 자동으로 얕은 clone과 Orca 등록을 요청한다. 비공개 저장소는 키가 없으면 등록 대기 상태가 될 수 있다.
3. **서버 키 준비**를 누르고 고정 작업자가 실행될 때까지 기다린다. 화면에는 공개키와 지문만 표시한다.
4. 저장소 관리 권한이 있는 사람이 GitHub 저장소 **Settings → Deploy keys → Add deploy key**에서 공개키를 등록하고 **Allow write access**를 선택한다. 개인 토큰을 서버에 입력하지 않는다.
5. 포털에서 **등록 후 읽기 연결 확인**을 누른다. SSH 읽기 확인과 Orca 폴더 등록 성공을 표시한다. 이는 쓰기 권한의 증명이 아니다.
6. Orca 터미널의 해당 폴더에서 팀원이 검토한 변경을 기능 브랜치에 실제 push해 쓰기를 별도로 확인한다. 테스트만을 위한 자동 커밋·push는 하지 않는다.

연결할 주소를 바꾸려면 먼저 연결을 해제한다. 기존 작업 폴더는 지우지 않으며 새 주소에 예약된 폴더를 사용한다. 실패 시 키 등록·주소·네트워크를 확인하고 다시 요청한다. GitHub의 공개키 등록은 수동 단계다.

## 보안·자원 한계

- 신뢰하는 3인 팀이 하나의 Orca OS 계정을 공유한다. 같은 계정은 다른 프로젝트 키도 읽을 수 있다. 저장소별 GitHub 권한 제한은 사용자별 서버 격리가 아니다.
- 개인키는 Orca 사용자 전용 `.ssh/kosmos-deploy`에 0600으로 생성하며 DB·API·백업에 넣지 않는다. SSH는 443 포트, 공식 GitHub Ed25519 호스트 키 고정과 엄격 검증을 사용한다.
- 기존 root 작업자가 고정된 작업 종류·정수 기반 키 경로만 처리한다. Git/Orca 자식 프로세스에는 DB·AWS 환경변수를 넘기지 않는다. 웹 입력을 셸 명령으로 실행하지 않는다.
- 단계 사이에 새 DB 트랜잭션으로 소유권·계정·작업 취소·연결 revision을 다시 확인한다. 이미 시작한 외부 작업의 일부 파일은 남을 수 있으므로 취소가 파일 작업의 원자적 롤백을 뜻하지 않는다.
- 기본 소유자당 연결 5개, clone 전 여유 공간 2GiB 확인은 완화 장치다. 공유 터미널의 직접 파일 쓰기에 대한 하드 디스크 할당량은 제공하지 않는다. 보존된 작업 폴더는 운영자가 별도 검토한다.
- 백업 v4는 소유권과 저장소 메타데이터를 보존하되 공개키도 비우고 새 키 등록 필요 상태로 저장한다. 실행 작업·개인키·Orca 폴더/연결은 복원하지 않는다. v3 복원도 지원한다.
