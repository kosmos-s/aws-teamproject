# Orca 프로젝트별 실행 환경 전환

프로젝트별 UID, 작업 디렉터리, 저장소 키, 브라우저 연결을 전환한다. 기존 공유 작업 공간은 운영자 전용 백업으로 보존한다. 팀원은 새 포털 링크로 다시 연결하고 필요한 경우 새 계정에서 AI에 로그인한다.

## 실행 환경 준비

1. 프로젝트 DB의 `orca_projects`와 `project_repositories` 행, 실제 체크아웃·워크트리, 진행 중인 명령을 읽기 전용으로 대조한다. 파일 내용, 키와 토큰은 출력하지 않는다. 종료 예약과 예상 작업 시간을 확인한다.
2. 프로젝트 ID마다 잠긴 암호와 로그인용 셸이 없는 `kosmos-orca-p<ID>` 계정·그룹을 준비한다. 홈은 `/var/lib/kosmos-orca-projects/<ID>`이고 소유자는 전용 계정, 모드는 `0700`이다. 부모 경로와 서비스 정의는 root가 소유한다. `projects`, 프로필 `.config/orca`, 키 디렉터리 `.ssh/kosmos-deploy`는 프로젝트가 소유한다. 브로커와 작업자도 같은 프로필을 사용한다. SSH로 해당 OS 계정에 직접 진입할 경로가 없는지 확인한다.
3. root만 수정할 수 있는 JSON 파일에 프로젝트 ID를 키로, `18000`–`18999` 범위에서 중복 없는 포트를 숫자 값으로 지정한다. 예를 들어 ID 10번에 포트 18681을 쓰는 경우 `{"10":18681}`이다. 포털 `ORCA_PROJECT_REGISTRY`와 방화벽의 `/etc/kosmos-orca-projects/firewall.env`는 동일한 절대 경로를 사용한다. 서비스 실행 전에 포트 점유 여부를 확인한다.
4. root 전용 `/etc/kosmos-orca-projects/<ID>.env`에 `ORCA_RUNTIME_PORT`, 프로젝트 계정의 `XDG_RUNTIME_DIR`, 일치하는 `DBUS_SESSION_BUS_ADDRESS`를 지정한다. 설치 환경의 Orca CLI·nftables·POSIX ACL 도구를 검증한다. 런타임 인스턴스의 root 관리 drop-in에서 `[Service]` 아래 `SocketBindAllow=ipv4:tcp:<PORT>`를 서비스에 할당된 포트 하나에만 설정한다. 전용 bind 제한이 실제 커널에서 적용되는지 테스트한다. 작업자와 브로커는 이 범위에 바인드할 필요가 없다.
5. 등록된 UID와 포트로 nftables 정책이 활성화된 후 두 프로젝트의 런타임과 브로커를 띄운다. 브로커 소켓은 프로젝트 소유이고 포털 계정만 명시적으로 통과시킨다. 같은 UID의 직접 연결과 다른 UID의 차단, 포털의 연결, 브로커의 브라우저용 페어링을 확인한다. 프로젝트 UID의 로컬 공유 런타임 접근도 차단한다. 동시에 공유 계정이나 다른 프로젝트에서 할당된 포트를 대신 바인드할 수 없는지도 확인한다.

## 기존 데이터 보존과 연결 전환

작업을 멈출 수 있는 시간에 공유 런타임과 연결 작업자의 활동을 확인한다. 기존 체크아웃을 수정하기 전에 각 프로젝트의 미커밋 파일·숨김 파일·워크트리 메타데이터를 보존한다. 절대 `gitdir`, 별도 `.git` 및 Git 대체 오브젝트를 사용하는 체크아웃은 프로젝트 소유의 새 위치에서 참조를 재검증한다. 운영에 필요한 프로젝트별 저장소 키만 같은 호스트의 전용 계정으로 이관하며, 이전 공유 계정에서 읽을 수 있는 복제본은 남기지 않는다. 백업은 root 전용이다. 기존 Orca 프로필, 브라우저 페어링, AI 로그인 설정은 새 홈으로 복제하지 않는다. 키와 작업자의 고정 `core.sshCommand`가 프로젝트 홈을 가리키고 대상 GitHub 저장소와 통신할 수 있는지 확인한다.

프로젝트별 Orca 등록, 실제 브라우저 연결, 멤버/비멤버 검사, 권한 회수 시 기존 연결 종료, 서로의 파일·키·포트 접근 거부를 두 프로젝트 이상에서 확인한다. 브라우저 정적 페이지가 기존 공유 런타임의 작업 제어 경로를 열지 않는지도 확인한다. 그다음에만 포털 레지스트리와 WebSocket 경로를 전환하고 기존 공유 실행 환경을 팀원에게 제공하던 경로를 끊는다. 폴더 목록·IMDS 제한·S3 첨부·백업·SSM을 함께 확인한다.

검증에 실패하면 신규 경로의 운영 노출을 중단하고, 이전 서비스 상태와 프로젝트 설정을 복구한다. 응답이 확인되기 전에 기존 데이터, 키 백업 또는 예약을 제거하지 않는다. `main`은 운영과 통합 후보가 모두 검증된 뒤 반영한다.
