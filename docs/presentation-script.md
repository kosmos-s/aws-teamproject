# 과제 공지 기준 20분 발표 대본

발표자: 김건보, 강태영, 박찬욱. 팀명 없음. 역할·개인별 기여·발표 구간은 사용자 확인 결과 미정이다.

기준: 사용자가 제공한 과제 공지 PPT 1·2·4장의 평가 항목. 23장, 설명 13분 45초와 시연·전환 6분 15초를 합한 20분 계획이다. 실제 리허설 시간을 측정한 결과는 아니다. 질의와 전환은 시연 여유 안에서 조정한다.

공지 기준: EC2는 한 대, Route 53은 생략 가능. 세 사람 구성은 공지의 4명 내외 안내와 실제 교수자 확인을 구분한다. AI 실제 요청·3인 동시 접속은 미검증이다.

## 01. AWS 기반 팀 공유
AI 개발환경 구축 및 운영 (00:00–00:20)

안녕하세요. 김건보, 강태영, 박찬욱입니다. 기존 Orca를 AWS EC2 한 대에 배포하고 팀 운영 포털을 직접 구현한 프로젝트입니다. 구성과 데이터 모델, 실제 검증, 운영과 복구를 설명하고 실행 결과를 시연하겠습니다.

근거: README.md, STATUS.md

## 02. 공유 개발환경에 운영 기록이 필요했습니다 (00:20–00:55)

목표로 삼은 상황은 팀원이 같은 서버의 개발환경을 사용하면서도 작업 기록과 상태를 함께 확인해야 하는 경우입니다. 코드 편집만 가능하면 누가 어떤 작업을 했는지, 서버가 정상인지, 파일이 어디에 저장되는지 확인하기 어렵습니다. 그래서 기존 편집 도구를 활용하면서 포털에 프로젝트와 메모, 첨부, 점검과 복구 기능을 모았습니다. 이는 사용자 조사 수치가 아니라 프로젝트에서 정한 문제와 목표입니다.

근거: AGENTS.md, README.md

## 03. 기존 Orca 위에 운영 포털을 구현했습니다 (00:55–01:30)

Orca와 Webmin, AWS 서비스는 기존 도구입니다. 자체 구현 범위는 FastAPI API와 HTML 화면, 로그인과 역할 제어, 업무 데이터 모델, 첨부 처리, 상태 점검, 백업과 복원입니다. 코드는 AI 도구의 작성 지원을 받았고 테스트와 AWS에서의 동작으로 검증했습니다. 새 IDE나 자체 에이전트 엔진을 개발했다고 주장하지 않습니다.

근거: AGENTS.md, app/, deploy/, docs/contributions.md

## 04. 브라우저에서 작업과 운영을 연결했습니다 (01:30–02:00)

사용자는 포털에 로그인한 뒤 프로젝트에 메모와 첨부를 남깁니다. Orca 매핑이 있는 프로젝트의 버튼으로 공유 개발환경을 열고 사이드바에서 저장소를 선택합니다. 새 포털 프로젝트를 만든다고 Git 저장소나 Orca 폴더가 자동 생성되지는 않습니다. 관리자는 별도 Webmin 계정으로 서비스와 로그를 확인합니다.

근거: docs/user-guide.md, app/templates/index.html, app/orca_gateway.py

## 05. 공개 HTTPS와 비공개 데이터를 분리했습니다 (02:00–02:45)

외부 접속은 도메인과 고정 EIP를 통해 Nginx의 HTTPS로 받습니다. 포털은 루프백에서 실행하고 Orca와 Webmin은 포털 인증 경로를 거칩니다. 운영 DB는 비공개 RDS이고 파일은 비공개 S3입니다. 웹 인바운드는 80과 443이며 Orca 6768과 Webmin 10000을 직접 공개하지 않습니다. ALB와 CloudFront는 핵심 경로가 아니라 별도 한시 시연으로 뒤에서 설명합니다.

근거: docs/course-demo.md, docs/architecture.md, deploy/

## 06. Python 웹 애플리케이션과 관리형 DB를 사용했습니다 (02:45–03:20)

EC2는 Ubuntu 24.04이고 포털 런타임은 Python 3.12입니다. FastAPI와 Uvicorn으로 API를 제공하고 SQLAlchemy로 RDS MySQL에 연결합니다. 화면은 단순 HTML과 CSS, JavaScript로 구성했습니다. 버전은 저장소의 고정 의존성과 배포 검증 기록에 근거합니다. 운영 DB의 비밀번호나 AWS 계정 식별자는 장표에 넣지 않았습니다.

근거: requirements.lock, docs/deployment.md, docs/verification.md

## 07. 계정·세션·차단 상태를 별도로 저장합니다 (03:20–04:00)

계정에는 사용자 이름과 암호 해시, 역할을 저장합니다. 하나의 사용자는 여러 세션을 가질 수 있고 차단 상태는 사용자 ID를 키로 별도 테이블에 기록합니다. 로그인 세션에는 원문 세션 토큰 대신 해시와 만료, CSRF 값을 저장합니다. 운영 이벤트는 점검·백업·보안 이력을 담는 독립 테이블입니다. 현재 구현의 실제 외래키 관계만 표시했습니다.

근거: app/models.py, app/security.py, docs/data-model.md

## 08. 프로젝트를 기준으로 메모·첨부·Orca를 연결합니다 (04:00–04:40)

프로젝트 하나에 여러 메모와 첨부가 연결됩니다. Orca 연결 매핑은 프로젝트당 없거나 하나입니다. 첨부 테이블에는 S3 객체 키와 파일 메타데이터를 두고 실제 파일 본문은 S3에 보관합니다. 메모의 author는 현재 문자열이며 사용자 테이블을 참조하는 외래키로 구현하지 않았습니다. Orca 자체 내부 DB는 이 ERD에 포함되지 않습니다.

근거: app/models.py, app/storage.py, docs/data-model.md

## 09. 점검 이력은 작게 보고 필요할 때 펼칩니다 (04:40–05:15)

이 화면은 11월 11일 공개 포털에서 직접 확인한 상태 요약입니다. 점검 이력은 사용성을 개선해 맨 아래로 옮겼습니다. 기본 최근 세 개를 보여주고 펼치면 현재 조회된 최근 최대 백 개의 상세 내용을 내부 스크롤로 볼 수 있습니다. 자동 새로고침 뒤에도 펼침 상태를 유지하며 모바일 화면에서도 가로 넘침이 없음을 확인했습니다. 이력은 입력 폼이 아니라 자동으로 쌓이는 조회 화면입니다.

근거: app/templates/index.html, app/static/app.js, docs/user-guide.md

## 10. 접근 회수는 열린 WebSocket에도 적용합니다 (05:15–05:50)

포털은 관리자, 팀원, 조회 전용 역할을 구분합니다. 로그인과 CSRF 검증, 관리자 자기 잠금 방지와 세션 회수를 구현했습니다. Orca 중계는 연결 시작 때뿐 아니라 세션 만료·차단을 재검증합니다. 실제 공개 연결에서 로그아웃 후 종료 코드 1008과 0.02초를 관측했습니다. 이는 한 번의 시험값이고 모든 환경의 성능 보장이 아닙니다. 포털 역할이 서버 프로세스의 사용자별 완전 격리를 뜻하지도 않습니다.

근거: app/team_controls.py, app/orca_gateway.py, docs/course-demo.md

## 11. 고정 대상 점검으로 실패와 복구를 기록합니다 (05:50–06:30)

약 1분마다 Orca TCP와 디스크를 확인하고 가능한 경우 CPU와 RAM 사용량도 기록합니다. TCP 연결이 성공했다고 AI 요청 성공으로 판단하지 않습니다. 실제로 Orca 서비스를 잠시 중지해 점검 실패가 기록되고 재시작 후 정상으로 돌아오는 것을 확인했습니다. 오래된 점검은 지연으로 표시합니다. 별도 외부 감시·메일 발송 로직도 구현했지만 실제 SMTP 발송은 아직 설정하지 않았습니다.

근거: app/ops.py, app/external_monitor.py, deploy/kosmos-monitor.timer, docs/verification.md

## 12. 업무 데이터와 Git 코드를 별도로 복구했습니다 (06:30–07:15)

매일 논리 백업을 실행하도록 구성했고 첨부와 백업의 크기, 보관 기간을 제한했습니다. 업무 데이터는 프로젝트와 메모, 첨부를 별도 SQLite와 폴더에 복원한 뒤 내용을 비교했습니다. 계정과 세션을 복원하는 백업은 아닙니다. Git 코드는 커밋의 추적 파일만 백업해 별도 폴더에 복원했습니다. 실제 54개 파일, 원문 약 202KB를 복구하고 README를 커밋 blob과 비교했습니다. 운영 데이터를 덮어쓰지 않았습니다.

근거: app/ops.py, app/code_backup.py, docs/verification.md

## 13. 설치·검증·서비스 관리 명령을 분리했습니다 (07:15–08:15)

초기 배포는 기존 AWS 자원과 권한을 확인한 뒤 SSM 관리 경로로 수행했습니다. 전용 가상환경에 고정 의존성을 설치하고 테스트했습니다. 포털은 systemd의 환경 파일로 DB와 S3 설정을 받고 루프백에서 실행하며 Nginx가 HTTPS를 제공합니다. 화면의 명령은 구조 설명용입니다. 실제 운영 자원이 이미 있으므로 초기 provision을 반복 실행하지 않습니다. 비밀번호를 셸 인수로 전달하거나 환경 파일을 source로 실행하지 않습니다.

근거: docs/deployment.md, scripts/remote.ps1, deploy/kosmos-portal.service, requirements.lock

## 14. GitHub에서 검토와 자동 테스트를 연결했습니다 (08:15–08:55)

소스는 GitHub 저장소에서 기능 브랜치로 관리했습니다. push와 PR 시 GitHub Actions가 Python 의존성을 설치하고 테스트, 컴파일, 셸 문법 검사를 실행합니다. 개발 중에는 실패 회귀 테스트와 코드 검토를 거쳤습니다. 다만 EC2 배포는 운영자가 승인한 스크립트를 실행하는 방식이므로 완전한 자동 CD가 아닙니다. 팀원별 실제 기여와 서버 GitHub 쓰기 인증도 별도 확인이 필요합니다.

근거: .github/workflows/tests.yml, docs/orca-workflow.md, docs/contributions.md

## 15. AI 개발 지원과 서버 AI 실행을 구분했습니다 (08:55–09:40)

개발에는 AI 코딩 도구의 지원을 받아 코드와 문서, 테스트를 작성하고 실제 결과로 검증했습니다. 운영 서버에는 Orca와 Codex를 준비했지만 사용자 요청으로 AI 로그인을 보류했습니다. 따라서 서버에서 실제 AI 요청이 성공했다고 말하지 않습니다. 공지에는 AI 활용 종류와 개발·적용 방법 설명이 포함됩니다. 별도의 RAG나 AI API를 새로 만들었다고 주장하지 않고, 현재 사용한 개발 지원과 앞으로 검증할 Codex Agent 작업을 구분합니다.

근거: AGENTS.md의 AI 로그인 보류, docs/deployment.md, docs/contributions.md

## 16. 강의의 AWS 서비스를 한시 시연까지 확인했습니다 (09:40–10:25)

공지의 EC2 한 대와 Route 53 생략 가능 조건을 반영했습니다. 기존 무료 DNS와 EIP, HTTPS를 사용했고 비공개 RDS와 S3를 앱에 연결했습니다. 추가 승인을 받아 ALB 상태 점검과 CloudFront 정적 안내 페이지도 실제 검증했습니다. 원본 S3는 익명 403이었습니다. 시연이 끝난 뒤에는 신규 ALB와 CloudFront, 별도 정적 버킷을 삭제했습니다. 핵심 포털 트래픽이 지금도 ALB를 지난다거나 고가용성이라는 주장은 하지 않습니다.

근거: 과제 공지 2장, docs/course-review.md, docs/course-demo.md

## 17. 동작 성공과 접근 차단을 함께 검증했습니다 (10:25–11:05)

테스트와 실제 AWS 사용을 구분해 확인했습니다. 기존 39개 테스트가 통과했고 공개 포털에서 프로젝트와 파일 저장, Orca의 편집과 명령 실행을 확인했습니다. 파일 시험 수정은 원본대로 복구했습니다. 익명 API는 401, S3 원본은 403으로 차단됐고 WebSocket 접근도 로그아웃에 따라 회수됐습니다. 중지 예약이 실제로 수행된 것과 시연 자원 삭제도 확인했습니다. 실제 세 사람의 동시 사용과 AI 요청은 이 검증으로 대체하지 않습니다.

근거: docs/verification.md, docs/course-demo.md, tests/, GitHub Actions

## 18. 운영 시간과 남는 비용까지 관리했습니다 (11:05–11:40)

비용은 서울 정가와 730시간 기준 환산 견적입니다. EC2와 EBS, 공인 IPv4 한 개의 견적은 24.45달러, RDS 컴퓨팅과 저장은 20.87달러로 소계 45.32달러이며 S3와 전송, 세금 등은 별도입니다. EC2와 RDS에 각각 서버 타이머와 일회성 AWS 종료 예약을 설정했습니다. 중지 후에도 EBS와 DB 저장, EIP 비용은 남고 RDS는 중지 7일 뒤 자동 재시작할 수 있습니다. 이후 추가 운영은 별도 사용자 승인 창을 따릅니다.

근거: docs/costs.md, STATUS.md; https://aws.amazon.com/vpc/pricing/; https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_StopInstance.html

## 19. 오류를 재현하고 원인을 확인해 수정했습니다 (11:40–12:20)

처음에는 EC2를 재시작하자 일반 공인 IP가 바뀌었습니다. 강의의 EIP 항목을 다시 확인해 탄력적 IP를 연결했고 중지 후에도 유지됨을 확인했습니다. ALB 대상은 EC2의 가용 영역이 빠져 unused 상태였는데 오류 설명과 실제 AZ를 대조해 수정한 뒤 정상 응답을 확인했습니다. 점검 기록은 길게 쌓여 주요 기능을 밀어내므로 화면 아래로 옮기고 최근 세 개와 펼침 화면으로 나눴습니다. 서비스 설치, 연결, 실제 작업 검증을 각각 구분해야 한다는 점도 배웠습니다.

근거: docs/course-demo.md, docs/verification.md, app/static/app.js

## 20. 팀의 실제 기여와 발표 역할을 기록합니다 (12:20–12:55)

참여자는 김건보, 강태영, 박찬욱입니다. 사용자가 현재 담당 업무와 발표 역할은 미정이라고 확인했습니다. 개인별 기여를 임의로 배정하지 않았습니다. 제출 전 각자의 실제 구현·검토·검증·자료 기여와 발표 구간을 정하고 근거를 남겨야 합니다. 앞으로의 분담 계획을 이미 수행한 사실로 발표하지 않습니다.

## 21. 공유 런타임의 한계와 남은 검증이 있습니다 (12:55–13:25)

## 예상 질문과 답변

**Orca를 직접 개발했나요?** 기존 Orca를 배포했다. 직접 구현한 부분은 FastAPI 운영 포털, 인증·역할·연결 회수, 데이터 관리와 운영 자동화다. AI 도구의 코드 작성 지원을 받았다.

**실제 AI 요청도 성공했나요?** 서버용 AI 로그인은 보류 중이다. 실제로 검증한 것은 원격 파일 편집·저장과 터미널 실행이다.

**왜 EC2가 한 대인가요?** 과제 범위를 한 대로 정했다. ALB의 2개 AZ 사용이 단일 앱 서버의 고가용성을 뜻하지 않는다.

**Route 53도 사용했나요?** 기존 무료 DNS로 도메인을 연결했다. 유료 Route 53 호스팅 영역은 만들지 않았다.

**왜 CloudFront를 삭제했나요?** 승인된 시연 기간에 별도 정적 안내 페이지를 실제 검증한 뒤 비용을 관리하기 위해 삭제했다. 현재 제공되는 포털 프런트는 EC2의 같은 출처다.

**백업을 만들기만 했나요?** RDS 논리 데이터는 별도 SQLite·폴더에 복원했고, 코드도 빈 폴더에 복원해 내용 일치를 확인했다. 새 RDS 스냅샷/PITR 또는 서버 전체 복원은 시험하지 않았다.

**세 명이 완전히 격리되나요?** 포털 역할은 구분하지만 Orca는 공유 런타임이다. 사용자별 프로세스·파일 격리나 동시 편집 충돌 해결을 제공한다고 주장하지 않는다.

**0.02초는 성능 보장인가요?** 공개 WebSocket 한 시험 세션에서 관측한 로그아웃 후 종료 시간이다. 다수 사용자·고부하 성능 지표가 아니다.

**중지하면 과금이 없어지나요?** EBS, RDS 저장소, EIP와 S3 저장 비용은 남는다. RDS는 중지 후 최대 7일 뒤 자동 재시작할 수 있다.

**왜 접속이 안 될 때가 있나요?** 승인된 운영 창 밖에서는 서버를 중지한다. 고정 IP는 주소를 유지할 뿐 중지된 서버를 실행하지 않는다.
