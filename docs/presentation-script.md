## 03. 공개 HTTPS와 비공개 데이터를 분리했습니다 (45초)

팀원은 도메인과 고정 공인 IP를 통해 Nginx에 연결합니다. Nginx 뒤의 포털은 루프백에서 실행하고 Orca와 Webmin도 인증 게이트웨이를 거칩니다. 운영 데이터는 비공개 RDS에, 첨부와 백업은 비공개 S3에 저장합니다. Orca 자체 내부 DB를 RDS로 옮기지는 않았습니다. 이 그림은 핵심 운영 구성이고, ALB와 CloudFront는 뒤에서 별도 강의 시연으로 설명합니다.

근거: docs/course-demo.md, docs/architecture.md, deploy/

## 04. 포털에서 개발환경과 서버 관리를 연결했습니다 (35초)

사용자는 포털 로그인 후 프로젝트를 선택하고 Orca에서 개발환경 열기를 누릅니다. 열린 공유 Orca에서 aws-teamproject를 선택해 파일 편집과 터미널을 사용합니다. 이 버튼이 프로젝트를 자동 선택하거나 사용자별로 완전히 격리하는 것은 아닙니다. 관리자는 별도 Webmin 계정으로 서비스와 로그를 확인합니다. Webmin의 2단계 인증 등록은 아직 남아 있습니다.

근거: docs/orca-access-verification.md, docs/orca-workflow.md, app/orca_gateway.py

포털은 프로젝트와 작업 메모, 작은 첨부 파일을 관리하고 점검과 백업 기록을 보여줍니다. 오른쪽은 11월 10일 초기 공개 포털 화면입니다. 이후 관리자 계정 제어와 공개 Orca 연결을 추가했고, 최신 동작은 API와 브라우저에서 별도로 검증했습니다. 화면의 당시 정상 표시는 현재 서버가 켜져 있다는 뜻은 아닙니다.

## 06. RDS와 S3를 실제 애플리케이션에 연결했습니다 (40초)

RDS에는 사용자와 세션, 프로젝트, 메모, 첨부 메타데이터와 운영 이력을 저장합니다. 파일 본문은 S3에 저장하고 앱에서 권한을 확인한 뒤 다운로드합니다. RDS는 비공개이며 EC2 보안 그룹에서만 접근하고 TLS 인증서를 검증합니다. S3는 공개 접근 차단과 암호화를 적용했습니다. 테스트와 논리 복원에는 별도의 SQLite를 사용했습니다.

근거: docs/data-model.md, app/models.py, app/storage.py, docs/verification.md

## 07. 로그아웃하면 열린 Orca 연결도 끊깁니다 (40초)

포털은 관리자, 팀원, 조회 전용 역할을 구분하고 CSRF 검증을 적용했습니다. WebSocket도 연결 시 한 번 확인하는 데서 끝내지 않고 세션 만료와 차단을 재검증합니다. 실제 공개 WebSocket을 열고 같은 시험 세션을 로그아웃했을 때 0.02초 후 1008 코드로 종료되는 것을 확인했습니다. 한 번의 관측값이므로 모든 상황의 응답시간 보장으로 말하지 않습니다. 공용 Orca는 사용자별 프로세스 격리를 제공하지 않습니다.

근거: app/team_controls.py, app/orca_gateway.py, docs/course-demo.md, tests/

## 09. 강의의 배포 요소를 실제 구성에 대응했습니다 (45초)

강의는 AWS 시작부터 EC2, 도메인, ELB, RDS, S3, CloudFront와 자원 정리까지 대조했습니다. 2장의 고정 공인 IP는 탄력적 IP로 적용했고 도메인은 기존 무료 DNS를 사용했습니다. Route 53 유료 호스팅 영역을 만들었다고 주장하지 않습니다. ALB와 CloudFront는 추가 승인으로 별도 시연한 뒤 비용 관리를 위해 삭제했습니다. 강의 문서의 모든 명령을 무조건 실행한 것은 아닙니다.

근거: docs/course-review.md, 제공 강의 1~8장 및 최종 프로젝트 PDF

## 10. ALB와 CloudFront는 별도 시연 후 정리했습니다 (45초)

핵심 포털의 HTTPS 경로는 유지하면서 ALB에는 상태 점검 경로만 연결했습니다. ALB의 기본 경로와 로그인 API는 404로 막았고 대상으로는 EC2의 HTTPS 443을 사용했습니다. 처음에는 EC2의 가용 영역이 빠져 unused였지만 원인을 확인하고 수정해 healthy와 200을 확인했습니다. CloudFront는 별도 비공개 S3 안내 페이지를 OAC로 읽어 HTTPS 200을 제공했고 S3 직접 요청은 403이었습니다. 두 시연 구성은 승인된 종료 후 삭제했습니다.

근거: docs/course-demo.md, docs/verification.md

## 11. 실제 AWS에서 동작과 차단을 확인했습니다 (35초)

테스트는 로컬과 EC2에서 39개를 통과했고 GitHub CI도 성공했습니다. 공개 브라우저에서 Orca 파일 저장과 터미널 실행을 확인하고, 검증용 파일 수정은 원본대로 복구했습니다. 인증 없는 포털 API는 401, S3 원본은 403으로 차단됐습니다. 이것은 AI 요청 성공이나 세 사람이 동시에 쓴 검증을 대체하지 않습니다.

EIP와 EBS, RDS 저장 비용은 남습니다. RDS는 7일 뒤 자동 재시작될 수 있으므로 다음 시연 또는 삭제 계획이 필요합니다.

## 예상 질문과 답변

**Orca를 직접 개발했나요?** 기존 Orca를 배포했다. 직접 구현한 부분은 FastAPI 운영 포털, 인증·역할·연결 회수, 데이터 관리와 운영 자동화다. AI 도구의 코드 작성 지원을 받았다.

**실제 AI 요청도 성공했나요?** 서버용 AI 로그인은 보류 중이다. 실제로 검증한 것은 원격 파일 편집·저장과 터미널 실행이다.

**왜 EC2가 한 대인가요?** 과제 범위를 한 대로 정했다. ALB의 2개 AZ 사용이 단일 앱 서버의 고가용성을 뜻하지 않는다.

**Route 53도 사용했나요?** 기존 무료 DNS로 도메인을 연결했다. 유료 Route 53 호스팅 영역은 만들지 않았다.

**왜 CloudFront를 삭제했나요?** 승인된 시연 기간에 별도 정적 안내 페이지를 실제 검증한 뒤 비용을 관리하기 위해 삭제했다. 현재 제공되는 포털 프런트는 EC2의 같은 출처다.

**백업을 만들기만 했나요?** RDS 논리 데이터는 별도 SQLite·폴더에 복원했고, 코드도 빈 폴더에 복원해 내용 일치를 확인했다. 새 RDS 스냅샷/PITR 또는 서버 전체 복원은 시험하지 않았다.

**세 명이 완전히 격리되나요?** 포털 역할은 구분하지만 Orca는 공유 런타임이다. 사용자별 프로세스·파일 격리나 동시 편집 충돌 해결을 제공한다고 주장하지 않는다.

**0.02초는 성능 보장인가요?** 공개 WebSocket 한 시험 세션에서 관측한 로그아웃 후 종료 시간이다. 다수 사용자·고부하 성능 지표가 아니다.

**중지하면 과금이 없어지나요?** EBS, RDS 저장소, EIP와 S3 저장 비용은 남는다. RDS는 중지 후 최대 7일 뒤 자동 재시작할 수 있다.

**왜 접속이 안 될 때가 있나요?** 승인된 운영 창 밖에서는 서버를 중지한다. 고정 IP는 주소를 유지할 뿐 중지된 서버를 실행하지 않는다.
