# Orca 계정의 EC2 메타데이터 접근 제한

`deploy/orca-imds-firewall.py`는 공유 `orca` 계정과 `kosmos-orca-p<프로젝트 ID>` 형식의 전용 계정을 찾는다. nftables 출력 체인에서 해당 UID의 IPv4·IPv6 메타데이터 목적지를 거부한다. 다른 계정에도 할당된 UID나 root UID를 발견하면 새 규칙을 적용하지 않는다. 전용 `inet kosmos_orca_imds` 테이블만 트랜잭션으로 교체한다.

## 적용 전 확인

- EC2 메타데이터 설정, `nft` 사용 가능 여부, 기존 방화벽 관리 방식과 정책 로드 순서, Orca 계정 UID를 확인한다. 관리자 계정이 관리하는 경로에 후보 스크립트와 서비스 정의를 설치한다.
- 새 프로젝트 UID는 서비스 시작 전에 정책에 반영한다. `kosmos-orca-imds.service`를 재로딩해 새 제한을 검증한다. 방화벽을 통째로 다시 로드하는 별도 서비스가 있으면 전용 테이블이 유지되는지를 함께 확인한다.
- 격리된 Ubuntu 테스트는 후보 테이블의 최초 적용, 변경 UID로 재적용, IPv4·IPv6 차단, 다른 UID와 다른 목적지 연결 유지, 별도 방화벽 테이블 보존을 확인했다. AWS의 실제 서비스 회귀 검증은 배포 이후 수행한다.

## 운영 적용과 복구

승인된 변경 창에서 서비스를 활성화한 후 Orca 계정의 메타데이터 연결 거부, 포털의 S3 첨부·백업, 관리자의 SSM 접속을 확인한다. 토큰과 역할 자격 증명을 읽거나 기록하는 방식은 사용하지 않는다. 설정한 AWS IPv6 메타데이터 활성 상태도 확인한다. 서비스 재시작과 재부팅 이후 전용 테이블이 남고 실제 접속이 거부됨을 검증한다.

되돌릴 때는 이 서비스를 비활성화하고 전용 `inet kosmos_orca_imds` 테이블만 제거한다. 기존 방화벽 설정을 재설치하거나 전체 규칙을 비우지 않는다. 설치 파일과 서비스 상태는 작업 전 상태에 맞춰 복구하고, 포털과 SSM이 응답하는지 확인한다.
